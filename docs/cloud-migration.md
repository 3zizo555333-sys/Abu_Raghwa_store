# تشغيل Supabase وVercel

> لا تُطبّق هذه التغييرات على قاعدة الإنتاج مباشرة. ابدأ بمشروع Supabase تجريبي منفصل، ثم اربط مستودع GitHub بمشروع Vercel تجريبي.

## Supabase

1. أنشئ مشروعًا تجريبيًا منفصلًا من لوحة Supabase، وخذ نسخة احتياطية كاملة لأي قاعدة مصدر قبل التغيير.
2. ثبّت Supabase CLI محليًا، ثم سجّل الدخول واربط مشروع الاختبار:
   ```sh
   supabase login
   supabase link --project-ref YOUR_TEST_PROJECT_REF
   supabase db push
   ```
3. راجع `supabase/migrations/202610080001_cloud_store.sql` قبل التطبيق. ينشئ الترحيل الجداول والسياسات ودوال RPC وbucket الصور الخاص وRealtime change feed.
4. أنشئ المستخدم الإداري أولًا في Supabase Auth. ثم خزّن القيمتين `SUPABASE_URL` و`SUPABASE_SERVICE_ROLE_KEY` في `.env.local` المستثنى من Git، وشغّل أمر التهيئة لمرة واحدة:
   ```sh
   pnpm supabase:provision-shop --name "أبو رغوة" --manager-user-id USER_UUID --confirm-one-time-provisioning
   ```
   راجع UUID واسم المحل قبل التنفيذ؛ المفتاح الخدمي لا يدخل إلى المتصفح ولا يُرسل في المحادثة.
5. تحقّق من سياسات RLS بتسجيل دخول مستخدمين من محلين مختلفين؛ لا ينبغي أن يعبر الاستعلام أي حد للمحل. تحقق من أن البائع لا يستلم حقول التكلفة، وأن الطلبات العامة لا تعرض بيانات الإدارة.
6. إعدادات Authentication يجب أن تتضمن نطاقات إعادة التوجيه لكل من Preview وProduction. لا تضع بيانات العرض أو الاقتران في query string يمكن نسخه؛ استخدم رموزًا قصيرة العمر مع hash بالخادم.

## Vercel

1. بعد تحويل واجهات الخادم إلى Functions (العمل ما زال مرحليًا)، اربط المستودع مع Vercel واجعل كل commit على فرع Pull Request ينشر Preview. إعداد البناء الساكن للواجهة: `pnpm install --frozen-lockfile` ثم `pnpm build:web`، والمخرج `dist/public`. لا تنشر Production من تكوين Express الحالي؛ لم يُستبدل كل API بعد.
2. أضف `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY` إلى Preview وProduction. المفتاح العام فقط يذهب إلى المتصفح.
3. أضف `SUPABASE_SERVICE_ROLE_KEY` إلى بيئة الخادم فقط عند وجود Function تحتاجه، مع قصر الدور والصلاحية. لا تستخدم `VITE_` أو `NEXT_PUBLIC_` لهذا السر. أضف `SUPABASE_DB_URL` لأدوات الترحيل/CI الموثوقة فقط عند الحاجة، لا لواجهة التطبيق.
4. لا تُوجّه Vercel إلى خادم Express دائم. يجب تحويل كل endpoint مستخدم إلى Function واختباره قبل قطع التطبيق القديم. تظل إعادة كتابة SPA لمسارات الصفحات منفصلة عن مسارات `/api/*`.
5. لا تُفعّل Production قبل نجاح Preview على قاعدة بيانات تجريبية وبمستخدمين فعليين من أدوار manager وseller.

## نقل البيانات القديمة بأمان

- خذ backup كاملًا من قاعدة MySQL الحالية؛ لا يمكن لهذا المستودع أو هذا السكربت إنشاء backup عن بُعد ما لم تُعطَ بيانات الاتصال وموافقة تشغيلية.
- صدّر بيانات المدير يدويًا من نسخة موثوقة إلى JSON مراجع. لا تجمع بيانات Local Storage من أجهزة الموظفين ولا تستوردها تلقائيًا.
- قبل تنفيذ الترحيل، ثبّت مخطط JSON لملف التصدير المعتمد وراجع تحويل كل الحقول والباركودات والفواتير. **لم يُفعّل بعد سكربت استيراد الإنتاج**؛ لا تستخدم كود استيراد ذاتيًا أو تستورد snapshot غير معتمد. يجب أن يدعم السكربت النهائي `--dry-run`، تقريرًا لكل سجل مرفوض، ومفتاح idempotency، وألا يحذف أي صف سحابي غائب عن التصدير.
- لا تنقل hashes كلمات المرور القديمة كما لو كانت كلمات مرور Supabase Auth. اختبر إعادة تعيين كلمات المرور أو دعوات Auth وأعد اعتماد الأدوار والعضويات قبل القطع.
- قارن عدد المنتجات/الفواتير والكمّيات والإجماليات وسجل كل باركود مكرر/سجل غير صالح في التقرير. أبق قاعدة المصدر read-only لفترة الاسترجاع المتفق عليها.

## تحقق الخدمة الحية

بعد وصول المشروع التجريبي والبيانات التجريبية: افتح جلستين مستقلتين لمستخدمين مصرحين، أنشئ/عدّل/احذف منتجًا، تحقق من الحدث خلال ثانيتين ثم أعد التحميل؛ أنشئ فاتورة على مخزون محدود وتأكد أن محاولة بيع متزامنة لا تتجاوز الرصيد؛ ارفع صورة JPEG/PNG/WebP أقل من 5 MB وتحقق من signed URL على جهاز ثانٍ، ثم اختبر رفض النوع/الحجم. لا يُعدّ نجاح unit tests بديلًا عن هذه الاختبارات الحية.
